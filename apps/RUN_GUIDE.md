# Apps — Run Guide

This page is the map for everything under `apps/`: what each of the four
applications publishes, what's genuinely different between them, and where to
go for the full, runnable walkthrough of each one. For cloning the repo,
setting up the conda environment, and configuring `.env` credentials, see the
top-level **[`README.md`](../README.md)** — that's all one-time setup shared
by every app and isn't repeated here.

## The four applications

| Application | Collection ID | What it publishes |
|---|---|---|
| **HydroLand** (`apps/hydroland/`) | `EO.UFZ.DAT.HYDROLAND` | Land surface hydrology from the Mesoscale Hydrologic Model (mHM/mRM): river discharge, soil moisture, plus decadal indicators (aridity index, discharge percentiles). Historical 1990–2014 + projection 2015–2049, 3 Climate DT models. |
| **HydroMet** (`apps/hydromet/`) | `EO.DWD.STAT.HYDROMET_EXTREMES` | Extreme precipitation statistics and an event catalogue, combining DWD's KOSTRA (depth-duration-frequency) and CatRaRE (radar-based events) products. |
| **Energy Indicators** (`apps/energy_indicators/`) | `EO.BSC.DAT.ENERGY_INDICATORS` | Energy-relevant indicators: wind capacity factors, heating/cooling degree-days, photovoltaic potential. Global, derived from hourly IFS-NEMO output. |
| **FWI** (`apps/fwi/`) | `EO.FMI.DAT.DESTINE_CLIMATE_WILDFIRE_FWI` | Fire Weather Index — daily fields, annual statistics, regional climatologies. |

## What to expect: the pipeline

All four apps follow the identical four-step pipeline and file layout:

```
raw application output
  → 1. stage.py    build the catalog skeleton from catalog_config.yaml alone — no
                    data files needed (collection.json + data/YYYY[/MM]/<item>/ folders)
  → 2. move.py     link/copy/move source NC/CSV files into the pre-built item folders
  → 3. update.py   write metadata/items/*.json (stac_dedl_core.ItemGenerator),
                    dropping any item with no asset
  → 4. upload      push metadata/ + data/ to s3://usergenerated-proposal-<id>/
                    (via run_pipeline.sh --upload, or stac_dedl_core.upload directly)
```

`stage.py`/`move.py`/`update.py` and `run_pipeline.sh` are app-specific files
(each app's source data shape differs), but they all follow the exact same CLI
conventions: `stage.py`/`move.py` are dry-run by default (`--execute` to
apply), `move.py` requires exactly one of `--link`/`--copy`/`--move` with no
default, and `update.py` always removes empty-asset items after generation.
Every app also has a `staging/delete_s3_collection_prefix.py` maintenance
utility and most have a `staging/check_data.sh` pre-staging QC script.

What's genuinely shared in code (not just convention) lives in
`stac_dedl_core/`: `appconfig.py` (loads `catalog_config.yaml` + resolves
`apps/_shared/simulations.yaml` keys), `collection_builder.py` (writes
`collection.json`/`collection_config.json`, including optional datacube
extension and multi-publication support), `update.py`/`s3_cleanup.py` (the
logic behind every app's `staging/update.py` and
`staging/delete_s3_collection_prefix.py`), and `generate_item_metadata.py`
(`ItemGenerator`, used unmodified by all four apps — no app maintains its own
fork).

## Three config keys that control item shape

Every `catalog_config.yaml` sets these three keys. They control how `stage.py`
lays out item folders under `data/` and how `update.py` reads them back — get
them wrong and items either don't get found, or files that should share one
item end up split across several (or vice versa).

- **`item_folder_level`** — how many directory levels sit between `data/` and
  an item folder: `YYYY` (`data/<year>/<item>/`, one folder per year — HydroMet),
  `MM` (`data/<year>/<month>/<item>/`, one folder per month — HydroLand, Energy
  Indicators, FWI), `DD`, or `NONE`. `stage.py` creates folders at this depth;
  `update.py` (`ItemGenerator._get_item_folders_by_level`) walks `data/` at
  exactly this depth to find them — set it to the level that doesn't change
  *within* one item (e.g. `MM` because every file in a monthly item shares the
  same year+month, but two different days don't need their own level).
- **`item_config_optional`** — whether each item folder is allowed to skip an
  `item_config.json` file (a per-item override for properties/bbox, written
  manually, not generated by any of these apps). `true` (every app here uses
  this): a missing file silently falls back to `collection_config.json`,
  which is the normal case since none of the four apps generate per-item
  config files — folder name + filename are the only source of metadata.
  `false` would make `update.py` raise `FileNotFoundError` for any item
  folder missing that file — only useful if you *do* want to hand-author
  per-item overrides and want a typo'd/missing file to fail loudly instead of
  silently falling back.
- **`split_data_type_items`** — whether `data_type` is appended to
  `property_order` (when `property_order:` isn't set explicitly in the yaml).
  Since the item folder name is built by joining `property_order` values,
  appending `data_type` means files with a different `data_type` (e.g.
  `mhm` vs `mrm`, or `monthly` vs `yearly`) land in **separate** item
  folders instead of being merged as assets of the same item. `true` for
  HydroLand (mhm/mrm) and FWI (monthly/yearly, see below); `false` for
  HydroMet and Energy Indicators, where every file for a given period/month
  belongs to one item regardless of what kind of product it is.

### `published_data_type_key` — renaming the data-type property for publication

`split_data_type_items: true` appends `data_type` to `property_order`. That name ends
up in two places: the item **folder name suffix** (as a value, e.g. `__aridity_index`)
and the **property key** in each item's JSON.

Item properties are built positionally, by zipping `additional_property_keys` from
`collection_config.json` against the folder-name suffix tokens. The key names therefore
live only in `collection_config.json` — folder names never contain them.

`published_data_type_key` renames just that published key, leaving `property_order`
(and so folder names, item IDs and asset hrefs) untouched:

```yaml
split_data_type_items: true
published_data_type_key: collection_data_type
```

HydroLand sets this because the items already published on the DEDL use
`collection_data_type`. Without it, newly generated items would say `data_type` and the
collection would carry two names for one field, breaking portal filtering.

⚠️ Do **not** try to achieve this by editing `property_order` directly. `stage.py`
filters with `[k for k in cfg.property_order if k != "data_type"]` and
`ordered_properties()` drops keys not in the list, so the token would be silently
stripped out of the item folder names.

## What differs between apps

| | HydroLand | HydroMet | Energy Indicators | FWI |
|---|---|---|---|---|
| `item_folder_level` | `MM` | `YYYY` | `MM` | `MM` |
| `item_config_optional` | `true` | `true` | `true` | `true` |
| `split_data_type_items` | `true` | `false` | `false` | `true` |
| Item granularity | monthly, split by `data_type` (mhm/mrm) | **one item per workflow experiment**, over its own period | monthly, no split | monthly **and** yearly coexist (`data_type`) |
| `property_order` | model, experiment, generation, **activity**, realization | model, experiment, generation, **realization**, activity, resolution | model, experiment, generation, **realization**, activity, resolution | model, experiment, generation, realization, **resolution, activity**, data_type |
| Property value style | `generation-2`, `realization-1` (prefixed) | bare `2`, `1` | bare `2`, `1` | bare `2`, `1` |
| `move.py` source shape | one flat folder per data type, OR legacy item-dir with metadata in the folder name | Climate DT workflow output (`<member>/EO.DWD.STAT.HYDROMET/data/<YYYY>/<item>/`), names kept as written; optional — the catalog can be built in place | `YYYY/MM/` folders, one call per source | one top-level dir containing all model subfolders, auto-discovered |
| Metadata flags on `move.py` | `--model/--experiment/--generation/--activity/--realization` | none — period and values come from the workflow's item folder names | `--model/--experiment/--generation/--realization/--activity/--resolution` | `--generation/--realization/--resolution` only (model from folder name, experiment/activity from filename year) |
| Extra per-app feature | decadal `indicators:` (period-level products, separate from monthly mhm/mrm) | `collection_root_dir: EO.DWD.STAT.HYDROMET` (the workflow's folder, the bucket root), two `sci:publications`, full datacube | inlined 17-variable datacube extension | none — least-confirmed config (see its notebook) |

## Machine-specific paths

Every `catalog_config.yaml` uses placeholder values for `app_data_dir` and
`catalog_home_dir` (e.g. `/path/to/data/mhm`, `/path/to/stac-catalog-output`).
The framework reads those two keys but always checks the environment variables
`APP_DATA_DIR` and `CATALOG_HOME_DIR` first, so you never need to edit the YAML
to point at your own data.

**`local_paths.sh`** at the repo root holds the real paths for the UFZ HPC and
the example data directories. Source it before running any pipeline:

```bash
# from the repo root
source local_paths.sh hydroland          # exports APP_DATA_DIR + CATALOG_HOME_DIR
cd apps/hydroland && bash run_pipeline.sh --execute
```

If you are on a different machine, copy the file and update the four
`*_DATA_DIR` variables at the top to match your local layout. You can also
export the variables directly in your shell without using the file:

```bash
export APP_DATA_DIR=/your/path/to/mhm/data
export CATALOG_HOME_DIR=/your/path/to/output
cd apps/hydroland && bash run_pipeline.sh --execute
```

The notebooks do the same thing in Python (`os.environ["CATALOG_HOME_DIR"] = ...`
at the top of each notebook) — every hardcoded path inside a notebook is marked
with a `# <-- HARDCODED PATH` comment so you know exactly what to change.

## Upload

All four apps target the same bucket convention:
`s3://usergenerated-proposal-<collection-id-lowercase>/<COLLECTION_ID>/...`, via
`stac_dedl_core.upload` (`python -m stac_dedl_core.upload <id> --root <dir> --execute`,
or `run_pipeline.sh --execute --upload`). Dry run by default; supports a `--year`
filter for per-year uploads. Requires `.env` credentials — see the
top-level README's "Configure credentials" section. None of the four apps have
actually uploaded through this path yet; all testing so far (including every
notebook above) is local only: stage → move → update.

### Uploading again: new, unchanged and changed items

The upload keeps no state of its own; it compares every local item with the
bucket, so results can be uploaded one after another (e.g. one HydroMet workflow
run at a time) without knowing what was uploaded before:

- **Order.** Collection metadata first, then item by item its data files and its
  item JSON last. An item is only listed once all its files are there; if a file
  fails, its JSON is not uploaded and a re-run completes it.
- **New item** (JSON not in the bucket): uploaded. Files already there with the
  same size and checksum are skipped, so an interrupted upload resumes.
- **Unchanged item** (same JSON, same files, sizes and checksums): skipped. Repeating
  an upload, or uploading with `--year`, is harmless.
- **Changed item** (e.g. a re-run of the same experiment): a conflict. The upload
  stops **before anything is sent** and lists the items and why they differ.
  `--replace` replaces them: the item JSON is deleted first (unpublished), files the
  new version no longer has are deleted, changed and new files uploaded, and the
  JSON last. Other items are never touched.

Uploads store an `md5` in each object's metadata. Objects uploaded before that
are compared by size only. `--overwrite` re-uploads everything, including
unchanged items and the collection metadata (needed after changing
`catalog_config.yaml`), but deletes nothing. With `--year`, only items under
`data/<year>/` are checked and uploaded.
